Reviewed `main` at **`c9280fc`**, extension **1.17.1**. The checkout was fast-forwarded from
`bf3166b` before review. Those intervening changes principally expand the website and README;
the extension findings below apply to the current code, including older paths still in use.

This is an audit, not an implementation change. Priorities describe recommended order of work:
**P1** = privacy/account control; **P2** = functional correctness or material performance;
**P3** = follow-up improvement. No critical remote exploit was established.

## Findings to fix first

### F1 — P1: Bind automatic settings backup to the selected Google account

**Location:** [`src/background.js:875`](../src/background.js#L875),
[`src/options/google-auth.js:64`](../src/options/google-auth.js#L64).

`googleSaveOnce()` checks that a stored `googleProfile` exists, obtains a silent token and calls
`accountSave(token)`. It does not resolve that token's profile and compare it with the selected
profile. The backend correctly keys a request to the token's account; it does not know which
account the extension UI intended. A changed Google browser session can therefore target a
different account from the one shown in Settings.

**Probe:** stored profile A, silent token for B, and a controlled profile resolver returning B.
The automatic save returned success and issued one settings POST with B's token, including the
selected allergen list. It never called the profile resolver to reject the mismatch.

**Improve:** validate token identity against the selected account before automatic saves, following
the identity check already used by purchase sync. Associate the linked-backup state with that
identity; refuse on a mismatch and ask the user to choose an account. Add regression coverage for
switching Google sessions outside the extension.

### F2 — P1: Recheck auto-save consent immediately before uploading

**Location:** [`src/background.js:878`](../src/background.js#L878),
[`src/background.js:954`](../src/background.js#L954).

The automatic backup reads consent before awaiting silent authentication. If auto-save is disabled
or the selected profile is removed/changed while authentication is pending, the operation resumes
and posts anyway. `networkRequest` checks the master enabled switch, not Google auto-save consent.

**Probe:** hold the token promise, switch `googleAutoSave` to false, then release the token.
One settings POST still occurs after opt-out.

**Improve:** give automatic saves a generation/account guard and recheck consent, identity and
linked state after asynchronous steps and immediately before POST. Keep explicit manual Save
behavior separate. Cancel pending automatic operations when the relevant state changes.

### F3 — P2: Allow local purchase-history deletion when Google is offline

**Location:** [`src/options/history.js:48`](../src/options/history.js#L48),
[`src/worker/purchase-history.js:84`](../src/worker/purchase-history.js#L84).

The UI awaits `auth()` before sending `purchaseDelete` when history has an owner. If authentication
fails, the worker's local clear/pending-remote-deletion logic is never reached. This contradicts
the confirmation text's promise that offline account deletion will remain pending.

**Real-browser probe:** seed one owned purchase, make Google token retrieval fail, confirm Delete.
Result: **one local record remained; `historyDeletePending` was false**.

**Improve:** clear local history and establish the remote-deletion tombstone first. Authenticate
only for the remote follow-up. Consider separate, explicit local-only and local-plus-account
choices, without allowing a later sync to resurrect deleted records. Test offline, cancelled
sign-in, account mismatch, restart and subsequent deletion completion.

### F4 — P2: Always show recorded warning flags in purchase hover details

**Location:** [`src/content/order-hover.js:28`](../src/content/order-hover.js#L28),
[`src/content/orders.js:53`](../src/content/orders.js#L53).

`record.flags` is rendered only in the final fallback branch, not when a recorded breakdown exists.
Binding hover also removes the badge's title, which previously included those flags. A new,
well-recorded purchase can therefore lose the warning in both the tooltip and hover dialog.

**Real-browser component probe:** a snapshot with a valid breakdown and `flags: ['Contains milk']`
opened a dialog containing the score/base but **no “Contains milk” warning**.

**Improve:** render recorded warnings independently of the breakdown branch, identify them as
recorded warning matches, and include them in accessible text. Preserve the rule that warning
choices never change the numerical score. Test modern snapshots and legacy fallback records.

### F5 — P2: Stop stale-score badges from creating their own mutation loop

**Location:** [`src/content/retailer.js:329`](../src/content/retailer.js#L329),
[`src/content/retailer.js:345`](../src/content/retailer.js#L345),
[`src/content/cart.js:105`](../src/content/cart.js#L105),
[`src/content/search.js:119`](../src/content/search.js#L119).

A pass paints the plain score, then changes its text to `77 · saved`. The next pass replaces that
with the plain score and marks it saved again. The page observer sees those child-list mutations
and schedules another pass. The cart and Amazon search code have related paint-then-mark paths.

**Real-browser probe on Target:** with one stale cached score and automatic rating/background
refresh disabled, the otherwise idle badge generated **10 text mutations in two seconds**.
That confirms the Target loop; the related cart/Amazon paths need the same idle-stability test.

**Improve:** make freshness part of the badge's complete render signature and update text/ARIA only
when that signature changes. Ignore extension-owned mutations where safe. Add a browser assertion
that an idle page stops mutating after initial rendering, for fresh/stale/pending/error states.

### F6 — P2: Make cache eviction respect the configured grace period

**Location:** [`src/background.js:446`](../src/background.js#L446),
[`src/engine/db/score-cache.js:109`](../src/engine/db/score-cache.js#L109).

Recall accepts a score for the freshness window plus `cacheGraceDays`. Housekeeping deletes it at
the end of the freshness window alone. Thus the configured seven- or thirty-day saved-score grace
works only while cleanup has not yet removed the record.

**Probe:** under Most up to date (one-day freshness) and seven-day grace, housekeeping removed a
two-day-old cached score even though it lies within the configured recall window.

**Improve:** distinguish refresh eligibility from physical retention. Retain the score and associated
label long enough for the allowed grace window, keep the hard storage cap, and continue enforcing
product identity, preferences and rule revision. Test housekeeping followed by recall, not only
recall against a hand-seeded cache.

### F7 — P2: Enumerate retailer tiles once per pass, rather than once per product

**Location:** [`src/content/retailer.js:167`](../src/content/retailer.js#L167),
[`src/content/retailer.js:325`](../src/content/retailer.js#L325).

`searchPass()` enumerates the page, then `currentTile()` calls `adapter.searchTiles(document)` again
for each candidate. This creates roughly quadratic parsing work, amplified by repeated completions,
hydration and the stale-badge loop above.

**Instrumented runner probe:** one pass on 10, 50 and 100 tiles invoked full tile enumeration **11,
51 and 101 times**, respectively. Each enumeration itself walks the result list.

**Improve:** construct a generation-scoped map/set of current product/anchor identities once per
pass. Recheck connection and generation after storage reads without reparsing the entire document
for every tile. Add deterministic operation-count checks and a browser test with a large dynamic list.

### F8 — P2: Recognize HTTP-200 “Press & Hold” challenges consistently

**Location:** [`src/content/retailer.js:248`](../src/content/retailer.js#L248),
[`src/content/cart.js:129`](../src/content/cart.js#L129).

The generic retailer-search challenge pattern omits “Press & Hold,” while the cart pattern includes
it. A 200 response with that heading is treated as a missing label, so the queue continues starting
requests instead of pausing. HTTP 403/429/503 handling does not cover this case.

**Controlled runner probe:** a 200 `Press & Hold` response left `throttled` false and started a
third request with four products queued.

**Improve:** share bounded challenge detection/status codes between search, carts and orders.
Pause safely and show “Store verification required,” distinct from “Label unavailable.” Let the user
complete verification normally; do not try to bypass it. Test 200 challenge pages as well as rate limits.

### F9 — P2: Keep hover details available on badges marked “saved”

**Location:** [`src/content/hover-card.js:21`](../src/content/hover-card.js#L21),
[`src/content/search.js:121`](../src/content/search.js#L121),
[`src/content/cart.js:107`](../src/content/cart.js#L107).

`scoreBadge()` accepts only badge text matching `^\d+$`. Saved badges intentionally read
`77 · saved`, so they are excluded even though they still represent a valid numeric rating.
This defeats hover/focus details precisely when the extension is reusing its local cache.

**Evidence:** direct producer/consumer mismatch: the same valid badge passes the matcher as `77`
and fails it after the saved-state suffix is added.

**Improve:** identify rated badges through explicit product/score/state attributes rather than
presentation text. Test mouse and keyboard opening for fresh and saved badges, with refresh both
on and off. Keep historical order details tied to their recorded score, not a reconstructed current score.

| P2 | Large history sync | [`purchase-history.js:70`](../src/worker/purchase-history.js#L70) uploads the entire merged history in 100-record batches on every sync. A 10,000-entry history means 100 history-write requests even without new purchases. [`apps-script.gs:340`](apps-script.gs#L340) reads the shared history sheet and reparses account rows on each batch under a global lock. Preserve deletion epochs and first-recorded ratings. This is a code-derived scaling risk, not a measured production timeout. |
| P2 | Preview-store feature parity | Generic retailer badges expose a score/title but do not have Amazon's breakdown machinery; the retailer runner caches the scalar score rather than the full input needed for offline detail. ## Recommended implementation order

1. Account binding and opt-out cancellation (F1–F2); offline local deletion (F3).
2. Recorded warnings and fresh/saved hover behavior (F4, F9).
3. Eliminate idle mutations and repeated tile parsing; honor retention grace (F5–F7).
4. Unify verification/error states and preview-store detail support (F8 and parity work).
5. Optimize delta sync with large-history measurements, then improve provenance, localization,
   real-world evidence and release/distribution polish.

Keep the existing rule hash/revision, source identity checks, first-recorded purchase snapshots,
account deletion epochs and explicit sharing consent intact. None of these findings requires an
arbitrary scoring-weight change. After fixes, repeat the existing shared tests and both real-browser
harnesses, adding focused regression cases for the reproduced conditions above.
